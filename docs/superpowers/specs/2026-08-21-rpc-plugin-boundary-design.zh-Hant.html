Orrery · 設計規格

把 plugin 邊界從連結期移到行程

把一個工具搬出 orrery 的二進位檔、放到管線的另一端，讓「新增一個工具」不再等於「fork 整個 host」。

日期 2026-08-21 狀態 設計，待審 前一份 AIToolKit plugin framework 已發布 Orrery-AIToolKit 0.0.1-dev.3

目標

把 claude 這個工具，從「編譯進 orrery」變成「由一個獨立行程描述、orrery 透過 JSON-RPC 與它對話」，讓第三方不用 fork orrery 就能新增工具。

這份規格只涵蓋前三個步驟：協定、決定傳輸方式是否可行的量測、轉發代理，以及讓 claude 的事實經過管線。搬遷 claude 的行為刻意留給下一份規格——等真實數字和一條能動的管線都存在之後再寫，而不是現在用猜的。

為什麼是這個形狀

已發布的版本問題在哪

Orrery-AIToolKit 0.0.1-dev.3 定義了開放的 AITool protocol 和一個 registry，orrery 也確實在啟動時把三個內建工具註冊進去了。但沒有任何東西讀它：33 個呼叫點仍然在迭代 Tool.allCases，而 Account.tool 仍然是封閉 enum。

所以今天註冊一個第三方工具，它什麼都拿不到——沒有帳號目錄、沒有指令處理、沒有 migration 覆蓋。唯一可觀察的效果是出現在 AIToolRegistry.shared.all 裡，而沒有任何 production 程式碼會呼叫它。

更根本的是，那個邊界是連結期的邊界。第三方得 fork orrery 並加一個 target 才能參與。那不是 plugin 系統。

怎麼分解

「第三方工具完整平權」對一份規格來說太大。考慮過兩條切法：按層切（先所有工具的事實、再身分、再行為），以及按工具切（一個工具一路做到底）。

按工具切勝出，因為只有它會測試到介面。按層切做完，只證明了八個靜態欄位裝得下三個工具的靜態資料——那本來就不會失敗。而 claude 是最複雜的那個（憑證解析、session 探索、sandbox 診斷、takeover 播種都有它的分支），把它一路做到底，才會逼出協定真正需要什麼。

codex 和 gemini 這階段繼續走現有的 BuiltInAITool 橋接，從 enum 取事實。registry 不在乎一份描述是從哪來的。

架構

邊界在行程

orrery-claude 是獨立執行檔，用 orrery-sync 已經在用的方式探索：ORRERY_CLAUDE_PATH → ~/.orrery/tools/ → PATH。它隨 orrery 一起發布，但用第三方完全相同的機制被載入。

代理本身就是一個 AITool

有兩個承重的結果：

  • 內建與第三方走同一條路。用這種方式發布 claude，本身就是在證明第三方那條路可用。
  • 傳輸變成逐工具、可逆的決定。如果某個工具的往返成本太高，就把它連進行程內——一個呼叫點都不用改。

管線上跑 JSON-RPC 2.0

以行分隔的 JSON-RPC，走 stdio——這正是 orrery 自己的 MCP server 已經在講的形狀：initialize 做版本與能力協商、標準錯誤碼。這不是重用那 499 行程式碼，MCP 是另一個協定。重用的是形狀，以及「這條路在這個 repo 裡走得通」這個已知事實。

另一個候選是 argv subcommand。否決的理由是它把行程模型寫進了協定：沒有 request id 就沒有並行請求，所以之後要換成常駐傳輸時，得重新設計協定而不是換掉底下的管路。 

initialize     → { protocolVersion, capabilities: { … } }
tool/describe  → { id, displayName, configDirectoryName, configDirEnvVar,
                   authLoginCommand, installCommand, sessionSubdirectories,
                   ansiColor }

行為方法留給後續規格。initialize 的 capabilities 讓 plugin 可以只實作一部分，而 host 不必為了「發現它沒有」而付一次往返；-32601 Method not found 是漏網那個的後備。

序列化屬於 DTO，不屬於 protocol

AITool 只 refine Sendable。wire 型別是一個獨立的具體 Codable struct。這正是當初把 Codable 從 protocol 拿掉是對的原因：protocol 無法 Decodable，而一個轉發代理也沒辦法乾淨地 conform 一個硬要 Codable 的 protocol。

失敗處理

信任邊界

plugin 以使用者的身分、使用者的權限執行。以下所有機制都不限制惡意 plugin——安裝它的那一刻就是信任決定。這些規則限制的是意外，以及避免一個壞掉的 plugin 讓 host 失去其他還好好的工具。

stdout 只屬於協定

診斷輸出一律走 stderr。host 讀到無法解析的行就跳過，而不是崩潰——這跟 orrery 的 MCP server 已經在做的容錯一致。

生命週期

讀降級，寫中止

答案缺席，可以呈現成缺席；但一個可能沒發生的動作，絕不回報成已完成。

少一個欄位仍然值得把帳號列出來。而把一份可能沒複製成功的憑證記錄成「已複製」，是那種看起來像成功的失敗。這份規格只有 tool/describe，而它是讀取：一個無法描述自己的 plugin，就是不註冊而已。

與一次性 migration 的互動

orrery 的一次性 migration 會記錄覆蓋了哪些工具（MigrationFlag，PR #53 已發布）。一個因為 plugin 載入失敗而缺席的工具，絕不能被記錄成已覆蓋，否則 plugin 修好之後它會被永遠跳過。

好消息是這件事已經自動成立：pending 從 registry 取候選，缺席的工具根本不在集合裡；而 markCovered 是聯集而非覆寫，所以之後那一次執行會接住它。但這必須有測試，不能當成自然發生的性質。

一個安裝期的差異

orrery-claude 隨 orrery 發布，所以它不存在＝安裝壞了，對 claude 是硬錯誤；第三方 plugin 不存在則是軟錯誤——那個工具消失，其他照常。這是包裝層面的差異，不是介面層面的：兩者走完全相同的協定路徑。

步驟

每一步結束時，claude 都仍然完全可用，而且有東西可以獨立驗證。

步驟 1

協定骨架與量測

在 AIToolKit 建 JSON-RPC 層：Transport、StdioTransport、InMemoryTransport、JSONRPCConnection，以及一個給 plugin 作者呼叫的 serve()。再加一個只回 initialize 和 tool/describe 的最小 plugin。

然後量測，而且要誠實地量：

  • 一次 spawn + initialize + tool/describe 的往返成本
  • 用 instrumentation 找出 orrery 真正的高頻呼叫點，而不是推理哪個「聽起來很頻繁」
為什麼這是驗收條件

因為在這次設計過程中，純推理已經給出過一次錯誤答案：Claude Code 的 statusline 被假設成高頻 RPC 客戶端，實際上它根本不呼叫 orrery——它直接讀設定目錄、直接查 Keychain。

驗收：一個數字，以及一份具名的真實熱路徑清單。如果數字不能接受，我們會在寫任何 claude 邏輯之前就知道。

步驟 2

RemoteAITool 與探索

代理、執行檔探索、initialize 握手、版本拒絕、以及遠端工具的註冊。此時在 production 上還不可觀察——沒有東西讀 registry——所以它的驗證完全在測試裡。

驗收：磁碟上存在的 plugin 執行檔會出現在 AIToolRegistry.all；而缺席、hang 住、crash、或版本不合的那些不會出現，也不會干擾其他工具。

步驟 3

claude 的事實過管線

orrery-claude 用 claude 真實的八個欄位回答 tool/describe。需要事實的呼叫點改從 registry 讀。codex 和 gemini 繼續走 enum 橋接。

驗收：整套測試在「claude 的事實來自另一個行程」的狀態下通過，而且 Tool 上 claude 專屬的事實屬性已經消失。

測試

多數測試不該 spawn

會 spawn 行程的測試在 CI 上又慢又 flaky。InMemoryTransport 承擔大部分測試，只有少數幾個真的開子行程去證明真實管線可用。當初為了「stdio 換 socket」引進的傳輸抽象，在這裡第二次付紅利。

逾時必須可注入

client 的逾時是參數，測試用毫秒級。這是對介面的設計約束、現在就決定——寫死十秒的逾時會產生一組沒人願意跑的測試。

假 plugin 同時也是一致性套件

行為它證明什麼
ok正常路徑
hang呼叫逾時會觸發
crash-after-initialize中途死亡有被處理
garbagestdout 出現非 JSON 不會弄死 host
noisy誤混入的 print() 會被跳過而非致命
partial截斷的回應有被處理
wrong-version不認識的主版本會被拒絕並說明

它同時是給第三方的一致性測試套件——plugin 作者可以拿它跑自己的執行檔。對一個 plugin 框架來說，這是實質交付物，不是附屬品。

最重要的斷言是否定式的

給定  一個載入失敗的 plugin
則    其他工具仍然註冊成功
且    失敗的那個工具【沒有】被記錄成已覆蓋
且    之後 plugin 修好再跑一次，它【確實】被覆蓋

只斷言「有丟出錯誤」，會漏掉「丟了錯誤，但狀態已經被改到一半」那種情況。

不在範圍內

  • 行為搬遷。accountInfo、session 探索、憑證複製、登入狀態搬移。下一份規格，等量測數字和能動的管線都有了再寫。
  • 目錄拆解能力——工具宣告自己哪些路徑與欄位屬於身分、哪些屬於共享。已記在 AIToolKit 的 README 當作方向；它是最大也最有價值的一塊，而且要等失敗機制驗證過再做，因為它動的是使用者的實際資料。
  • Account.tool 的開放。仍然是封閉 enum，第三方工具還不能擁有帳號。屬於子專案 B。
  • Workspace.isolatedSessionTools——設計途中發現的第二處 enum 洩漏進持久化格式。跟子專案 B 一起做。
  • 常駐或 socket 傳輸。協定允許，但在量測要求之前不做。

刻意延後的問題

一個工具不理、但必須從繼承環境清掉的變數

gemini 宣告 configDirEnvVar == nil，因為 gemini-cli 只讀 $HOME/.gemini；但 PR #52 仍然需要 GEMINI_CONFIG_DIR 這個字面名稱，當作要從子行程環境中移除的 key。AITool 目前無法同時表達這兩個事實。

延後的理由是：在還沒有人實作 gemini 之前就為它設計欄位，是猜測。等 gemini 真的有 plugin 時，這個問題才會變成具體的。

register 對重複 id 是否該拒絕而非取代

目前是取代，所以第三方可以註冊 "claude" 把內建工具擠掉。拒絕大概是對的，配合內建先註冊。這是對已發布套件的行為變更，現在改最便宜——但這份規格的三個步驟並不需要它。
