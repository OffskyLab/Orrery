Design spec · Orrery

AIToolKit

把 orrery 的 per-tool 支援從封閉的 Tool enum，變成一套開放的 plugin framework — Claude 也是 plugin，第三方不必改 orrery 本體就能加新工具。

設計已確認 · 尚未實作 2026-08-21 docs/superpowers/specs/

為什麼

三個動機，都被列為主要：

1 · 別的工具會拖累 core

Gemini 就是活生生的例子：上游拿掉了 gemini auth login 子指令、gemini-cli 根本不理會 orrery 在設的 config dir 變數，最後 Google 直接封鎖個人版 Code Assist 帳號使用這個 client。沒有一件是 orrery 造成的，但每一件都落在 orrery 的 core、測試和發布節奏上。

2 · 第三方應該能自己加工具

想支援 Cursor 或 Copilot CLI 的人，不該需要去改 Tool.swift。

3 · 縮小維護面積

core 的測試、文件、發布只需要顧 framework 和 Claude；其他工具走自己的生命週期。

動機 2 是決定性的那個。 它排除了所有便宜的替代方案（把非 Claude 工具標成 experimental、或乾脆刪掉），因為那些都產生不出擴充點。

framework 已經是主體。 約 85% 的程式碼——帳號池、workspace、memory、session 共享、run/delegate、MCP、setup、shell 生成——本來就與工具無關。這比 「重寫 orrery」小得多。

而且模式已經存在一半。 AccountDirectoryRuntime.makeManager 加上 ToolAccountManaging protocol，正是這個設計需要的註冊接縫，只是範圍限縮在帳號目錄。 ThirdPartyRuntime 是同一套注入慣用法的第二個實例。AIToolKit 是把 codebase 已經信任的模式一般化，不是引入外來概念。

核心洞見

Tool 現在同時扛兩個不相干的職責：

身分 — 一個穩定字串，被當成字典 key、路徑片段（accounts/claude/…）、 JSON 值（metadata.json 的 "tool": "claude"）、以及 CLI flag（--claude）。

行為 — envVarName、defaultConfigDir、 authLoginCommand、ansiColor、sessionSubdirectories 等等。

這兩者可以分開拆，而且按這個順序拆才安全。行為可以搬走，身分原封不動 — 這代表整個第一階段不需要任何 on-disk migration，也不動 CLI。

把整個 enum 寫出來值得，因為它一次定案了線該畫在哪：

public enum Tool: String, Codable, CaseIterable, Sendable {
    case claude
    case codex
    case gemini

    public var envVarName: String            // CLAUDE_CONFIG_DIR / CODEX_HOME / GEMINI_CONFIG_DIR
    public var subdirectory: String          // rawValue
    public var defaultConfigDir: URL         // ~/.claude / ~/.codex / ~/.gemini
    public var displayName: String
    public var installCommand: [String]?
    public var installCommandDisplay: String
    public var supportsSetup: Bool           // installCommand != nil
    public var authLoginCommand: [String]?
    public var ansiColor: String
    public var coloredTag: String
    public var sessionSubdirectories: [String]
}

十一個成員裡，只有兩個是身分 —— rawValue，以及 subdirectory（它就是 rawValue）。其餘九個全是行為。 這個比例比「把身分和行為分開」這句話聽起來的要懸殊得多。

這個 enum 讓一個限制浮現
CaseIterable + 三個寫死的 case，是一個封閉世界。

在第三方依賴的 framework 裡這是致命的：加一個工具就等於改 framework 本身， AIToolKit 會從擴充點變成瓶頸。但把 enum 留在 orrery 當「白名單」也只是把封閉性從 framework 搬到宿主 —— 它仍然是一份編譯進去的三個名字，第三方依然加不了第四個。 所以 enum 哪裡都不留。

取而代之：struct + 註冊

AITool 是 AIToolKit 裡的一個 struct，裝的就是 enum 原本那些成員 （id、envVarName、defaultConfigDir、 authLoginCommand…）。每個工具自己建構一份描述自己，然後註冊給 orrery。

Tool.allCases 變成 registry.all —— 答案來自註冊了什麼，而不是編譯進了什麼。啟動時註冊在這個 codebase 已有前例： OrreryAccountKitRuntime.register() 和 OrreryThirdPartyRuntime.register() 現在就是從 main.swift 呼叫的。

on-disk 相容性仍然保住：AITool 透過 id 做 Codable， metadata.json 照樣讀寫 "tool": "claude"。

這個轉變帶進來的危險

CaseIterable 在編譯期是完整的；registry 只有在 註冊執行過之後才完整。這個差別不是修辭 —— 但危險的地方比乍看少， 而這個區分正是讓修法變小的關鍵。

安全的：所有 per-tool guard。 OriginTakeoverBootstrap （!store.isOriginManaged(tool:)）和 OriginAccountSeeder （origin.account(for: tool) == nil）雖然都在跑 Tool.allCases， 但它們沒有全域旗標、每次執行都會重跑。後來才註冊的工具下一個指令就會被撿到，會自癒。

危險的：AccountMigration 裡那四個旗標保護的一次性遷移。

旗標檔函式
.migration-v3runIfNeeded
.backfill-account-info-v1runInfoBackfillIfNeeded
.account-config-consolidatedrunAccountConfigConsolidationIfNeeded
.workspace-structure-relocatedrunWorkspaceStructureRelocationIfNeeded

每一個都只寫一個全域的「做完了」標記。如果某個工具在其中一個執行的當下沒有註冊，它會被跳過 —— 而旗標照樣寫下去。那台機器上，那個工具就永遠不會被遷移了。失敗是隱形且永久的。

因此以下不是選配：註冊必須在任何 migration / takeover / seeding 之前完成， 並在 main.swift 明確排序；一次性旗標改成 per-tool、或記錄它涵蓋了哪些工具， 讓後來才註冊的工具仍能補到；加一個測試斷言第一個旗標保護的流程執行時 registry 已完整。

Repo 佈局

AIToolKit 從第一天就是獨立 repo，以 Swift package 發布，不是 orrery 的 target。

這不是為了整齊，是被動機 2 逼出來的。寫 orrery-codex-support 的人必須能 只依賴那個 protocol。如果 AIToolKit 住在 orrery 裡面，每個 plugin 都得把整個應用程式 —— 指令、帳號 store、shell 產生器 —— 整包拉進來才碰得到一個介面。那不是任何人會接受的依賴， 而且會讓「第三方能加工具」紙面上成立、實際上不成立。

接受的代價

第一天就拆，代表 Phase 1 期間每次介面調整都是跨 repo 的版本鼓動，而不是本地一次編輯。這比較慢， 而且是刻意選的 —— 另一個選項（介面磨定前先留在 orrery 內）雖然迭代快，但依賴 故事要到最後才正確，而且介面很容易不知不覺伸手進 orrery 的內部型別。

因此需要的紀律

AIToolKit 在 Phase 1 全程停在 0.x，明確允許 breaking change，從 1.0 起遵守 semver。AIToolKit 內不得引用任何 orrery 型別。

orrery 內部分層

早期草稿讓 AIToolKit 吸收 OrreryAccountKit。那是錯的，而錯的理由值得寫下來，因為它同時 給了整個 framework 的判準：帳號管理是 orrery 的發明，不是工具的。 Claude Code、Codex、gemini-cli 都沒有「帳號池」這個概念 — 每個只知道自己有一個 config 目錄，是 orrery 在上面疊了池化。把帳號管理折進工具抽象，等於把消費者塞進被消費者裡面。

判準
AIToolKit 陳述工具的事實。AccountKit 決定 orrery 的政策。

實例：「gemini-cli 只讀 $HOME/.gemini、無視 GEMINI_CONFIG_DIR」是關於 gemini 的事實 — 屬於 AIToolKit。 「所以要蓋一層 wrapper 目錄放 .gemini → <account dir> 並重導 HOME」是 orrery 的隔離政策 — 屬於 AccountKit。同理 privateSubdirs / baseSharedSubdirs 是 orrery 的共享政策， 不是工具的屬性，留在 AccountKit。

能力歸屬

Claude 也是 plugin，不是特權案例。如果 Claude 能繞過介面，介面就永遠不會被它最嚴苛的 消費者壓測，第三方會撞上維護者從沒感受過的牆。

但「全部都變成 plugin 能力」會是過度抽象。套用上面的事實／政策判準：

機制歸屬理由
Phantom registry、liveness、supervisor shim loopcore確實與工具無關
--resume 語意、session id 探索AIToolKit工具如何 resume，是事實
憑證存放位置（Keychain item vs config 內檔案）AIToolKitCredentialAdapter 已有雛形
把憑證匯入池化帳號AccountKit池化是 orrery 的想法
啟動／結束時的設定檔 merge / splitAIToolKit只有 Claude 需要，但形狀可一般化
auth_success 通知AIToolKit「工具能告訴我們登入完成了」
帳號目錄共享政策AccountKitorrery 的政策，非工具屬性
shell wrapper function 貢獻AIToolKit最沒有前例 — 見風險
OAuth token refreshAIToolKit各家細節不同

能力是選配的。每個 plugin 只實作它的工具需要的子集；Claude 會實作最多 — 這正是讓介面保持誠實的原因。

分階段

0

framework repo 先存在

建立 AIToolKit repo，裡面只有 protocol 骨架。orrery 以 SPM 依賴引入。這時還沒有任何行為 搬家 —— 這一階段存在的意義是：之後每一個介面決定，都是在第三方將來消費它的那個地方 做的，而不是事後回頭補。

1

enum 讓位給 registry

是 strangler 不是重寫。AITool 與 registry 先出現，既有 enum 橋接過去（每個 case 產生一份描述），呼叫點就能一次搬幾個、兩種形狀並存。 等到沒有人再讀它，enum 才刪掉。

階段內的順序，因為這一步對單一 PR 來說太大：

  1. AITool + registry 就位；enum 橋接；註冊在 main.swift 排到所有 migration 路徑之前
  2. 先修上面那個一次性旗標的危險，再動任何呼叫點 —— 這一步不能延後
  3. 行為按能力搬家：憑證 → 啟動／結束 → shell → phantom
  4. Tool.allCases → registry.all，24 處
  5. 刪掉 enum
on-disk 格式不變 動機 1 · 2 · 3

--claude / --codex / --gemini 保留成 orrery 自己的便利 flag，對映到已註冊的 id。它們是宿主 UI，不是 framework 介面；沒有專屬 flag 的工具仍可用泛用方式指定。

那 62 個 per-tool switch 不是額外工作 —— 其中絕大多數就是正在搬家的 行為本身，會在第 3 步一併消化，而不是另一場遷移。

2

拆 plugin

把 Codex 和 Gemini plugin 移到各自的 repo（orrery-codex-support、 orrery-gemini-support），各自只依賴 AIToolKit。

載入機制刻意留白，等 1a/1b 顯示介面真正需要什麼再決定。但要注意它跟 Phase 0 的選擇有交互作用：如果 plugin 是編譯期 SPM 依賴，AIToolKit 作為 Swift package 就完全正確，但 orrery 仍得在自己的 Package.swift 裡列出每個 plugin —— 第三方能不經 orrery 同意就建置，卻不能出貨。真正獨立出貨 需要「被探索到的執行檔 + 線路協定」，那時候 Swift package 的重要性反而低於協定文件本身。 早點拆 AIToolKit 兩種情況下都是對的；它本身沒有直接帶來的，是 runtime 可插拔。

相容性約束

1a 與 1b 期間不可妥協：

  • metadata.json 保持 "tool": "claude"
  • 帳號路徑保持 accounts/<tool>/<id>/
  • --claude / --codex / --gemini 繼續可用
  • 既有安裝不得需要重新登入或遷移

風險

shell 片段貢獻毫無前例

ShellFunctionGenerator 是把 claude() / gemini() 當字面文字吐出來的。讓 plugin 貢獻 shell 是整個設計裡最沒被設計過的一塊，也最可能需要 自己一輪設計。而且它是介面爛掉代價最高的地方 — 產出會被寫進使用者的 rc 檔。

62 個 switch 點是實打實的重構

用 strangler 形狀緩解（protocol 與 enum 並存、逐步遷移、最後才刪），但仍會橫跨多個 PR。

Phantom 的 core／plugin 邊界目前只是推測

「registry 和 shim 與工具無關、只有 resume 語意因工具而異」這個主張看似合理但未經驗證 — 從來沒有非 Claude 的工具被 supervise 過。1a 不該試圖解決它。

Gemini 可能無論如何都撐不住

Google 已封鎖個人版 Code Assist 帳號使用 gemini-cli。既有 gemini 帳號是否還能運作尚未查證。 如果 gemini 支援在上游已死，Phase 2 的意義本身就改變了 — 動手前值得先確認。

不做什麼

  • Runtime 動態載入（dlopen）。Swift ABI 與 macOS 簽章都不適合 — 產出這份設計的那個 session，才因為一個單純的 cp 破壞簽章而吃到 SIGKILL。
  • 改動 on-disk 格式。
  • 重寫 phantom。
  • 在這次工作裡順便加新工具。

待決問題

  1. Phase 1 內部的五個步驟各自是一個 PR，還是能力遷移那步再細切？
  2. Codex 和 Gemini 在 1b 之前都留在 repo 內，到 Phase 2 才搬？（假設是）
  3. gemini 的上游封鎖，是否改變了 Gemini 值不值得繼續帶著？
  4. AccountKit 最終是否也該有自己的 repo？它是 orrery 自己的層而非 per-tool 的，所以大概不用 — 但如果 AIToolKit 真的在 orrery 之外也能重用，問題就不一樣了。
  5. 剩下那幾個 Claude 專屬的命令放哪 — _prepare-claude-launch、 _capture-claude-exit、orrery-claude-hook？它們是進入點不是 library code，可能需要自己一套 plugin 機制，而不是套進 AITool struct。
