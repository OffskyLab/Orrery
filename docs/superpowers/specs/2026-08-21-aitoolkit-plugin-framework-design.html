Design spec · Orrery

AIToolKit

把 orrery 的 per-tool 支援從封閉的 Tool enum，變成一套開放的 plugin framework — Claude 也是 plugin，第三方不必改 orrery 本體就能加新工具。

設計已確認 · 尚未實作 2026-08-21 docs/superpowers/specs/

為什麼

三個動機，都被列為主要：

1 · 別的工具會拖累 core

Gemini 就是活生生的例子：上游拿掉了 gemini auth login 子指令、gemini-cli 根本不理會 orrery 在設的 config dir 變數，最後 Google 直接封鎖個人版 Code Assist 帳號使用這個 client。沒有一件是 orrery 造成的，但每一件都落在 orrery 的 core、測試和發布節奏上。

2 · 第三方應該能自己加工具

想支援 Cursor 或 Copilot CLI 的人，不該需要去改 Tool.swift。

3 · 縮小維護面積

core 的測試、文件、發布只需要顧 framework 和 Claude；其他工具走自己的生命週期。

動機 2 是決定性的那個。 它排除了所有便宜的替代方案（把非 Claude 工具標成 experimental、或乾脆刪掉），因為那些都產生不出擴充點。

framework 已經是主體。 約 85% 的程式碼——帳號池、workspace、memory、session 共享、run/delegate、MCP、setup、shell 生成——本來就與工具無關。這比 「重寫 orrery」小得多。

而且模式已經存在一半。 AccountDirectoryRuntime.makeManager 加上 ToolAccountManaging protocol，正是這個設計需要的註冊接縫，只是範圍限縮在帳號目錄。 ThirdPartyRuntime 是同一套注入慣用法的第二個實例。AIToolKit 是把 codebase 已經信任的模式一般化，不是引入外來概念。

核心洞見

Tool 現在同時扛兩個不相干的職責：

身分 — 一個穩定字串，被當成字典 key、路徑片段（accounts/claude/…）、 JSON 值（metadata.json 的 "tool": "claude"）、以及 CLI flag（--claude）。

行為 — envVarName、defaultConfigDir、 authLoginCommand、ansiColor、sessionSubdirectories 等等。

這兩者可以分開拆，而且按這個順序拆才安全。行為可以搬走，身分原封不動 — 這代表整個第一階段不需要任何 on-disk migration，也不動 CLI。

分層

OrreryCore指令、workspace、memory、session
▲
OrreryAccountKitorrery 的帳號池 — 維持原樣
▲
AIToolKit工具「是什麼」：啟動、config 位置、登入、resume

早期草稿讓 AIToolKit 吸收 OrreryAccountKit。那是錯的，而錯的理由值得寫下來，因為它同時 給了整個 framework 的判準：帳號管理是 orrery 的發明，不是工具的。 Claude Code、Codex、gemini-cli 都沒有「帳號池」這個概念 — 每個只知道自己有一個 config 目錄，是 orrery 在上面疊了池化。把帳號管理折進工具抽象，等於把消費者塞進被消費者裡面。

判準
AIToolKit 陳述工具的事實。AccountKit 決定 orrery 的政策。

實例：「gemini-cli 只讀 $HOME/.gemini、無視 GEMINI_CONFIG_DIR」是關於 gemini 的事實 — 屬於 AIToolKit。 「所以要蓋一層 wrapper 目錄放 .gemini → <account dir> 並重導 HOME」是 orrery 的隔離政策 — 屬於 AccountKit。同理 privateSubdirs / baseSharedSubdirs 是 orrery 的共享政策， 不是工具的屬性，留在 AccountKit。

能力歸屬

Claude 也是 plugin，不是特權案例。如果 Claude 能繞過介面，介面就永遠不會被它最嚴苛的 消費者壓測，第三方會撞上維護者從沒感受過的牆。

但「全部都變成 plugin 能力」會是過度抽象。套用上面的事實／政策判準：

機制歸屬理由
Phantom registry、liveness、supervisor shim loopcore確實與工具無關
--resume 語意、session id 探索AIToolKit工具如何 resume，是事實
憑證存放位置（Keychain item vs config 內檔案）AIToolKitCredentialAdapter 已有雛形
把憑證匯入池化帳號AccountKit池化是 orrery 的想法
啟動／結束時的設定檔 merge / splitAIToolKit只有 Claude 需要，但形狀可一般化
auth_success 通知AIToolKit「工具能告訴我們登入完成了」
帳號目錄共享政策AccountKitorrery 的政策，非工具屬性
shell wrapper function 貢獻AIToolKit最沒有前例 — 見風險
OAuth token refreshAIToolKit各家細節不同

能力是選配的。每個 plugin 只實作它的工具需要的子集；Claude 會實作最多 — 這正是讓介面保持誠實的原因。

分階段

1a

行為搬家，身分不動

引入 ToolPlugin + ToolRegistry，把行為從 Tool enum 搬到三個 plugin。enum 原封不動留著當 ToolID。

on-disk 格式不變 CLI 不變 動機 1 · 3（部分） 動機 2 尚未達成

結束時第三方擴充仍需改 enum。這個中間狀態是刻意接受的 — 用它換取風險大幅下降。

1b

身分開放

把 enum 換成 String-backed 的 ToolID struct，透過 registry 查表。 Tool.allCases 和 ArgumentParser 的靜態 --claude flag 這些真正麻煩的東西，在這一步才需要解。

動機 2
2

拆 repo

把 Codex 和 Gemini plugin 移到各自的 repo（orrery-codex-support、 orrery-gemini-support）。載入機制 — 編譯期 SPM 依賴，還是用約定協定溝通的獨立執行檔 — 刻意留白，等 1a/1b 顯示介面真正需要什麼再決定。現在選就是用猜的。

相容性約束

1a 與 1b 期間不可妥協：

  • metadata.json 保持 "tool": "claude"
  • 帳號路徑保持 accounts/<tool>/<id>/
  • --claude / --codex / --gemini 繼續可用
  • 既有安裝不得需要重新登入或遷移

風險

shell 片段貢獻毫無前例

ShellFunctionGenerator 是把 claude() / gemini() 當字面文字吐出來的。讓 plugin 貢獻 shell 是整個設計裡最沒被設計過的一塊，也最可能需要 自己一輪設計。而且它是介面爛掉代價最高的地方 — 產出會被寫進使用者的 rc 檔。

62 個 switch 點是實打實的重構

用 strangler 形狀緩解（protocol 與 enum 並存、逐步遷移、最後才刪），但仍會橫跨多個 PR。

Phantom 的 core／plugin 邊界目前只是推測

「registry 和 shim 與工具無關、只有 resume 語意因工具而異」這個主張看似合理但未經驗證 — 從來沒有非 Claude 的工具被 supervise 過。1a 不該試圖解決它。

Gemini 可能無論如何都撐不住

Google 已封鎖個人版 Code Assist 帳號使用 gemini-cli。既有 gemini 帳號是否還能運作尚未查證。 如果 gemini 支援在上游已死，Phase 2 的意義本身就改變了 — 動手前值得先確認。

不做什麼

  • Runtime 動態載入（dlopen）。Swift ABI 與 macOS 簽章都不適合 — 產出這份設計的那個 session，才因為一個單純的 cp 破壞簽章而吃到 SIGKILL。
  • 改動 on-disk 格式。
  • 重寫 phantom。
  • 在這次工作裡順便加新工具。

待決問題

  1. Phase 1a 是一個 PR 還是多個？（建議多個，一次一個能力：憑證 → 啟動／結束 → shell → phantom）
  2. Codex 和 Gemini 在 1b 之前都留在 repo 內，到 Phase 2 才搬？（假設是）
  3. gemini 的上游封鎖，是否改變了 Gemini 值不值得繼續帶著？
  4. AccountKit 最終是否也該有自己的 repo？它是 orrery 自己的層而非 per-tool 的，所以大概不用 — 但如果 AIToolKit 真的在 orrery 之外也能重用，問題就不一樣了。
  5. 剩下那幾個 Claude 專屬的命令放哪 — _prepare-claude-launch、 _capture-claude-exit、orrery-claude-hook？它們是進入點不是 library code，可能需要自己一套 plugin 機制，而不是套進 ToolPlugin protocol。
